# 0006. Per-environment secret items from a checked-in manifest

**Status:** Accepted

## Context

Provisioning moves every credential through a secret manager: the value is
stored there first and piped into GitHub or Convex by path
(`op read "op://<vault>/<project> dev/convex/deploy-key" | gh secret set …`).
A path is only as good as the item behind it. Built by hand, items drift — a
label with a space, a field outside its section, an environment suffix — and
each drift breaks a documented pipe in a way nothing checks.

The natural-looking fixes both fail. Describing the layout in prose (the
previous state of `docs/SETUP.md`) leaves the shape to the reader, which is
where the drift comes from. Scripting the secret manager directly binds the
template to one vendor, and the template's contract is only "a secret store
with a CLI that reads values while a human is present"; not every project
uses the same store, and no generic CLI creates items with sections and
labels.

Two smaller choices were also open. One item per project with env-suffixed
labels (`deploy-key-dev`) looks simpler than one item per environment. And
the secret Better Auth signs sessions with could keep being generated at
deploy time, outside the store.

## Decision

- `scripts/secrets.manifest.json` is the source of truth for the item shape:
  the environments, the sections, the field labels, which fields are secret,
  which one is generated, and which one is prefilled. `docs/SETUP.md` refers
  to it and never lists the fields a second time.
- `scripts/secrets-scaffold.mjs` turns the manifest into items. It has one
  writer, for the 1Password CLI, and no writer interface. Any other store
  gets the manifest printed as a checklist (`--print`) and builds the items by
  hand under the same names, so every documented path still resolves.
- One item per environment, `<project> dev` and `<project> prod`, in the
  project's own vault. Field labels carry no environment qualifier; the item
  name does. Account-level values are duplicated into both items rather than
  split into a shared item, so one path form covers every value.
- The session-signing secret (`convex / auth-secret`) is generated by the
  script into each item, one value per environment, and never printed. The
  deploy step reads it from the item.
- The script creates; it never edits. An existing item stops the run before
  anything is written.

## Consequences

- **Positive:** the shape is data, versioned with the template, and the same
  data drives the checklist for stores the script cannot write to. Every
  `op://…` path in the docs is derivable from one file. A dev secret leak
  cannot forge prod sessions, and prod values can never be picked up from a
  dev item by mistake.
- **Accepted trade-off:** account-level values exist twice and must be
  updated twice. A second store gets no automation until someone writes its
  writer; the manifest is designed so that writer is the only new code.
- **Open:** a `--check` mode that compares an existing item against the
  manifest, for items built before the script existed. Editing existing items
  in place is deliberately out; a wrong edit on a live secret item costs more
  than a manual fix.
